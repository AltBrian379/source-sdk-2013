OWTF2 - Adding a 10th playable class ("Veteran")
=================================================

Goal
----
Make a new class that appears in the class menu, can be picked, and spawns as a
player who can walk around the level. It borrows the Sniper's model, stats and
sounds, and has no weapons or abilities yet. This is the base the Soldier: 76
style hero will be built on.

The class is called "Veteran" in code and in game (TF_CLASS_VETERAN, raw name
"veteran"). That is a working name: CLAUDE.md says the hero must get an original
name and must not use Blizzard's names. Renaming later means changing the enum,
the strings in tf_shareddefs.cpp, the class script, the .res button and the
localization tokens.

Every code change is marked with an "// OWTF2:" comment. To list them all:
    git grep -n "OWTF2:"


1. Where the new class sits in the enum, and why
------------------------------------------------
File: src/game/shared/tf/tf_shareddefs.h

The class list is the ETFClass enum:

    UNDEFINED=0, SCOUT=1, SNIPER, SOLDIER, DEMOMAN, MEDIC, HEAVY, PYRO, SPY,
    ENGINEER=9, [VETERAN=10], CIVILIAN, COUNT_ALL, RANDOM

Valve's comment says "Add any new classes after Engineer", so Veteran is 10.
That moved Civilian from 10 to 11, the class count from 11 to 12, and Random
from 12 to 13.

Why there and not at the very end: the game decides "is this a real, pickable
class?" with the range Scout..(Civilian-1). It does this in IsValidTFPlayerClass
and in the FOR_EACH_NORMAL_PLAYER_CLASS loops. Putting Veteran before Civilian
makes it pickable everywhere for free. Putting it after Civilian would have meant
special-casing it in dozens of places.

The cost: hundreds of places in the code size arrays or loop using these numbers,
and many tables list one entry per class. Each one had to be checked.


2. The main risk: tables that are one entry short
-------------------------------------------------
A C++ table like this

    const char *names[TF_LAST_NORMAL_CLASS] = { "", "scout", ..., "engineer" };

still compiles when the size grows from 10 to 11. The missing last entry is
silently filled with NULL (or 0). Nothing fails until a Veteran player hits that
table, and then the game crashes or shows garbage.

So the work was mostly an audit. I searched for every use of TF_CLASS_COUNT_ALL,
TF_LAST_NORMAL_CLASS, TF_CLASS_CIVILIAN, TF_CLASS_RANDOM and TF_CLASS_MENU_BUTTONS,
plus every table with a row for Engineer, and read each one. Where a table was
indexed by class, I added a Veteran row. Where it made sense, I also added a
COMPILE_TIME_ASSERT that checks the table's length. If someone adds an 11th class
later and forgets a row, the build fails instead of the game crashing.


3. What changed, file by file
-----------------------------
Shared code (compiled into both client and server)

  tf_shareddefs.h
    - TF_CLASS_VETERAN added to the enum.
    - The scoreboard class-icon tables hold "alive" icons, then "dead" icons,
      and code jumped to the dead ones with a hard-coded "+ 9". That breaks with
      10 classes. Replaced by TF_CLASS_ICON_DEAD_OFFSET, computed from the class
      count, and SCOREBOARD_CLASS_ICONS (was a hard-coded 19).

  tf_shareddefs.cpp
    - Class name tables (localized, plain, raw, short): added "Veteran".
    - Robot model and promo item tables: Sniper's entries for Veteran.
    - Weapon-name translation table: empty entries for Veteran (no weapons).
    - Class menu order (iRemapIndexToClass): Veteran is menu slot 10.
    - Scoreboard and portrait icon tables: Sniper's art for Veteran.
    - Teleporter "bread" models: one more entry, because the teleporter picks
      from this list using the class count. Without it, it would read past the
      end of the list.

  tf_classdata.cpp
    - Loads scripts/playerclasses/veteran.txt for the new class.

  tf_gamerules.cpp
    - Eye height per class: the table was declared [11], which is now one too
      small, so Civilian would have read past the end. Resized to the class count,
      with a Veteran row of 75 to match the Sniper body.
    - Freeze-cam achievement tables: a 0 row for Veteran.
    - Tournament class limits: new cvar tf_tournament_classlimit_veteran.
    - "Strange" weapon kill counters per victim class: these only exist for the
      9 stock classes. The lookup used "<= TF_LAST_NORMAL_CLASS", which already
      read past the end for Civilian. It now checks the table's size, so classes
      without a counter are skipped.

  tf_item_constants.h, tf_item_schema.cpp
    - The item system sized its per-class arrays with LOADOUT_COUNT, hard-coded
      to 10+1. Slot 10 was a dummy "Invalid" class. Veteran now takes slot 10,
      and Civilian (11) would have fallen outside. Raised to 11+1, with asserts
      that it matches the class count.
    - Added "Veteran" to the schema's class list.
    - "Usable by all classes" stays limited to the 9 stock classes. No stock
      item lists Veteran, so otherwise no item would count as all-class anymore.
    - Item models given as a per-class pattern (for example ring_%s.mdl) are no
      longer expanded for Veteran. The files don't exist, so the game kept
      trying to load models/.../ring_Veteran.mdl and failing.

  tf_weapon_passtime_gun.cpp
    - PASS Time throw speed and arc per class: Veteran uses the Soldier's for now.

Server only

  tf_gamestats.cpp   - Class name list for stats logging: "TF_CLASS_VETERAN".
  vscript_server.cpp - Scripts can use Constants.ETFClass.TF_CLASS_VETERAN.

Client only

  vgui/tf_classmenu.cpp (the class selection screen)
    - New "veteran" button. Its position comes from ClassSelection.res (below).
    - Count labels, team-count images and menu order tables: Veteran rows.
    - Veteran has no class menu music, so it plays the Sniper's.
    - Stock TF2 numbers its menu music and chalkboard tips with the old enum, in
      which Random was 12. Random is now 13, so those two lookups map Random back
      to 12 (GetStockContentClassIndex).
    - The selected-button image uses the Sniper art (no veteran art exists).
    - "Edit Loadout" is hidden for Veteran because it has no item loadout.

  vgui/charinfo_loadout_subpanel.h, replay/vgui/replaybrowserdetailspanel.h
    - The loadout screen has one button per class and would have crashed
      reaching for a missing 10th button. It stays limited to the 9 stock
      classes for now.

  tf_tips.cpp/.h, tf_hud_mann_vs_machine_loss.cpp
    - MvM loading tips store a general bucket as class number 10, which used to
      equal the last class number. That is now named TF_MVM_TIP_GENERAL_BUCKET,
      so Veteran (also 10) doesn't confuse it. This also fixes an old wrap-around
      that could pick bucket 0.

  c_tf_player.cpp            - Head gib models: Sniper's for Veteran. The lookup
                               has no bounds check, so a missing row would crash.
  tf_hud_playerstatus.cpp    - HUD class portrait (bottom left): Sniper's.
  tf_hud_arena_class_layout.cpp, tf_hud_itemeffectmeter.cpp, tf_statsummary.cpp,
  tf_steamstats.cpp, tf_playermodelpanel.cpp, item_quickswitch.cpp,
  class_loadout_panel.cpp    - Veteran rows in their per-class tables.
  tf_clientscoreboard.cpp, tf_hud_mann_vs_machine_scoreboard.cpp,
  tf_teamstatus.cpp          - "+ 9" replaced by TF_CLASS_ICON_DEAD_OFFSET.

Left alone on purpose
  - Spy's disguise menu is a fixed 9-class menu. Veteran isn't in it.
  - Bots pick from fixed class lists, so they never choose Veteran.
  - Training mode only covers 4 stock classes.
  - The class menu number keys only go 1-9, so Veteran has no hotkey.


4. Game content (game/mod_tf)
-----------------------------
  scripts/playerclasses/veteran.txt
    The class definition: model, hands, health 125, speed 300, death sounds.
    TF2 ships these files encrypted (.ctx), but the game reads a plain .txt
    first if one exists. I decrypted the shipped sniper.ctx with the SDK's own
    decryption code, only to copy the Sniper's real values. The values are
    placeholders until the hero gets tuned.

  resource/ui/ClassSelection.res and ClassSelection_SC.res
    Overrides of TF2's class menu layout (the second one is for Steam
    Controller). Generated from the stock files:
      - The class row moves 20 units left. Veteran goes right after Spy, and
        the gap before Random is a bit smaller, so it all still fits a 4:3
        screen.
      - Veteran's button sends "select 10". Random's button had "select 12"
        hard-coded, so it now sends "select 13".

  resource/mod_tf_english.txt
    TF_Class_Name_Veteran, a loading-screen tip (Tip_10_*) and a class-menu
    chalkboard tip (ClassTips_10_*).

=================================================
Ability 1: Sprint
=================================================

What it does
------------
The Veteran presses the Class ability key (+attack4, SHIFT by default) to
toggle Sprint on or off. While it's on, max movement speed is multiplied by
tf_veteran_sprint_speed_mult (default 1.5, i.e. +50%: 300 -> 450). Sprint
turns off on every spawn.

The multiplier is a convar so it can be tuned without rebuilding, e.g.
"tf_veteran_sprint_speed_mult 1.3". It's replicated: the server's value is sent
to clients so their movement prediction matches. Any server operator can change
it (it's not a cheat cvar).

A new key: +attack4
-------------------
TF2 already has +attack3 (Special attack). Nothing used +attack4, so:
  - src/game/shared/in_buttons.h: new button bit IN_ATTACK4 (bit 26). The
    usercmd already sends all 32 button bits, so no network change was needed.
  - src/game/client/in_main.cpp: +attack4 / -attack4 commands, wired up exactly
    like +attack3.
  - game/mod_tf/scripts/kb_act.lst (copy of TF2's, with two rows added): adds
    "+attack4" to Options > Keyboard, as "Class ability" in the Combat section
    and as "Veteran: Sprint (toggle)" in the class-specific section.
  - game/mod_tf/scripts/kb_def.lst: SHIFT -> +attack4 for "Use Defaults".
  - game/mod_tf/cfg/config_default.cfg (copy of TF2's, plus one line): new
    players start with SHIFT bound. Stock TF2 doesn't bind SHIFT to anything,
    so nothing is displaced.
  - Your local cfg/config.cfg (gitignored) also got the SHIFT bind.

How it works
------------
  - State: CTFPlayerShared::m_bVeteranSprinting. It's in the local-player
    network table and the prediction table, so the client predicts the toggle
    and the server corrects it if they disagree.
  - Logic: src/game/shared/tf/tf_veteran_abilities.cpp (new file, compiled
    into both client and server):
      Veteran_AbilityPostFrame  - runs every command from CTFPlayer::ItemPostFrame,
                                  on the server and in client prediction. A fresh
                                  press of +attack4 flips Sprint and recomputes speed.
      Veteran_GetMaxSpeedMultiplier - applied at the end of
                                  CTFPlayer::TeamFortress_CalculateMaxSpeed, after
                                  all of TF2's own speed modifiers.
      Veteran_ResetAbilities    - called from CTFPlayerShared::Spawn. If Sprint was
                                  on, it also recalculates max speed. Without that,
                                  a player who respawned mid-sprint kept 450 speed
                                  (found by the in-game test).
  - The new files are listed in client_tf.vpc and server_tf.vpc.
  - TF2's movement code caps speed at 520 (TF_MAX_SPEED). Sprint at 1.5x on
    300 base is 450, under the cap.

Not done yet
------------
  - No HUD indicator.
  - Sprint doesn't end when firing or using another ability. Overwatch's sprint
    does, but there's nothing to fire yet.
  - Sprint works in every direction, not just forward.

How it was tested
-----------------
A temporary VScript test (mapspawn.nut on itemtest) joined as Veteran and
pressed the real +attack4 through the client input path. It walked and measured
max speed and actual ground speed. Run with +tf_veteran_sprint_speed_mult 1.6:
  sprint off 300/300, on 480/480, off 300/300, on again 480/480,
  respawn while sprinting -> off, 300; Sniper pressing +attack4 -> 300 (no effect).
VScript can't set this convar at runtime, because the mod has no
vscript_convar_allowlist.txt. That's why the test sets it on the command line.
In one early run a scripted key press didn't register. It didn't happen again in
the next two runs.


=================================================
Weapon: the Veteran's rifle (placeholder)
=================================================

What it is
----------
The Veteran's one and only weapon, in the primary slot. In code it's
tf_weapon_veteran_rifle (class CTFVeteranRifle, weapon ID TF_WEAPON_VETERAN_RIFLE),
and in game it's called "Tactical Rifle". That's an original placeholder name;
the hero's real weapon name is Blizzard's. For now it is a plain subclass of the
SMG with the SMG's script, so it fires exactly like the SMG: 25-round clip, 75
reserve, SMG model and sounds. Its own mechanics come later.

It's built like every other TF2 weapon: a weapon entity, a weapon script, and an
item definition in the item schema. It shows up in the loadout screen like
stock weapons do.

New files
---------
  src/game/shared/tf/tf_weapon_veteran_rifle.cpp/.h
      The weapon entity. A CTFSMG subclass with its own network class, entity
      name and weapon ID.
  src/game/shared/tf/tf_owtf2_items.cpp/.h
      Loads the mod's item definitions. TF2's items_game.txt is checked against
      a signature file, so the mod can't ship a modified copy. Instead, right
      after TF2's schema is parsed (CEconItemSchema::BInitTextBuffer), this code
      merges scripts/items/items_owtf2.txt into it. The console shows
      "OWTF2: merged N entries" with -dev.
  game/mod_tf/scripts/items/items_owtf2.txt
      Item 60000, OWTF2_WEAPON_VETERAN_RIFLE: base item (the default weapon),
      primary slot, used only by the Veteran. It has no prefab: TF2's SMG prefab
      would also make it usable by the Sniper. "anim_slot SECONDARY" makes the
      Sniper body play its SMG animations.
  game/mod_tf/scripts/tf_weapon_veteran_rifle.txt
      Copy of TF2's SMG weapon script (decrypted). Changed: display name,
      WeaponType primary (so the game treats it as a primary for things like
      rage crits), primary ammo, weapon-selection bucket 0.

Changes to existing code
------------------------
  tf_shareddefs.h/.cpp  TF_WEAPON_VETERAN_RIFLE added at the end of the weapon
                        list, where Valve's comment says to (it keeps old demos
                        working), plus its name and damage type (same as the SMG).
  econ_item_schema.cpp  Calls the merge above (TF builds only).
  client_tf.vpc, server_tf.vpc  The four new source files.

Loadout screen
--------------
  - charinfo_loadout_subpanel.cpp and resource/ui/CharInfoLoadoutSubPanel.res:
    the class row on the Loadout screen has a Veteran button again (Sniper art
    for now). NUM_CLASSES_IN_LOADOUT_PANEL is back to its original definition,
    which now includes the Veteran.
  - class_loadout_panel.cpp: a slot layout for the Veteran that shows only the
    primary weapon slot. Secondary and melee are hidden. Cosmetic, action and
    taunt slots are kept, like other classes.
  - item_quickswitch.cpp: the Veteran's quick-switch row has only the primary.
  - tf_classmenu.cpp: "Edit Loadout" is shown for the Veteran again.

Content
-------
  - veteran.txt: primary ammo reserve 75. Health and speed are unchanged.
  - mod_tf_english.txt: weapon name, type and description strings.

How it was tested (VScript test on itemtest, then removed)
------------------------------------------------------------
  - The schema merge ran on both the server and the client.
  - The Veteran spawned with exactly one weapon: tf_weapon_veteran_rifle,
    item 60000, slot 0, clip 25, reserve 75. Holding fire dropped the clip to 10.
  - Screenshots: first-person view model (SMG with Sniper arms, ammo HUD 19/75),
    third-person Sniper body holding the SMG, the Loadout class row with 10
    classes, and the Veteran loadout page showing only "Tactical Rifle".
  - The Sniper still spawns with Sniper Rifle, SMG and Kukri. The new item isn't
    usable by him.


=================================================
Ultimate: HUD meter (UI only)
=================================================

What it is
----------
The Veteran's ultimate charge meter. It's a copy of the Medic's Ubercharge
meter: same background art, label, bar and full-charge pulse. The label reads
"ULTIMATE: 45%". It only displays a value. Nothing charges the ultimate or
spends it yet; that's the mechanic, which comes later.

How it works
------------
  - State: CTFPlayerShared::m_flVeteranUltCharge, 0 to 100, sent to the owning
    player (local-player network table, like the Soldier's rage meter).
    Get/SetVeteranUltCharge clamp it to 0-100. It survives death and respawn
    (as in the source game); Veteran_ResetAbilities leaves it alone.
  - HUD: src/game/client/tf/tf_hud_veteran_ultimate.cpp (CHudVeteranUltimateMeter),
    a trimmed copy of tf_hud_mediccharge.cpp. It draws only for a living local
    Veteran, and it's hidden by the same HUD flag as the Medic meter.
  - Layout: game/mod_tf/resource/ui/HudVeteranUltimate.res, a copy of TF2's
    HudMedicCharge.res without the Vaccinator-only controls. Its first block
    positions the panel itself: bottom centre (x c-65, y r69), where the source
    game shows the ultimate and clear of the ammo counter. TF2 positions the
    Medic's meter in scripts/hudlayout.res instead. Not overriding that file
    keeps the mod from freezing a copy of TF2's whole HUD layout. The cost is a
    harmless developer-console warning: "Hud element 'CHudVeteranUltimateMeter'
    doesn't have an entry ... in scripts/HudLayout.res".
  - Full-charge effect: at 100% the meter plays TF2's own HudMedicCharged
    animation, the Ubercharge pulse, and HudMedicChargedStop when it drops below
    100%. Those animations target child panels named ChargeLabel and
    ChargeMeter, which the copied layout keeps. So no animation files are
    overridden.
  - Strings: OWTF2_Ultimate "ULTIMATE: %charge%%%" and OWTF2_UltimateMinHUD,
    same format as TF2's Ubercharge strings.
  - Testing aid: tf_veteran_ult_charge_set <0-100> (cheat, server command).

Placeholders: the Medic's red/blue meter background, including its health-cross
icon.

How it was tested (VScript test on itemtest, then removed)
------------------------------------------------------------
  Screenshots at 0%, 45% (bar partly filled, "ULTIMATE: 45%"), 100% (full bar;
  a second shot a moment later shows the pulse dimming it), and 30% after the
  pulse stopped. Setting 250 is clamped to 100. The charge stayed at 100 through
  a respawn. As Sniper, the meter isn't shown.


=================================================
Ultimate system (charge, use, drain)
=================================================

Goal
----
A reusable ultimate system for any hero class, built the way TF2 handles per-class
meters: state in CTFPlayerShared, per-class values in the class script,
server-side rules and tuning convars.

Rules
-----
  - Each class sets its cost in its class script ("ultimate_cost"). 0 means no
    ultimate. "ultimate_duration" is how long the charge drains once used; 0
    means it's spent instantly. Veteran: 2310 and 6 (approximately the source
    hero's values; tune in veteran.txt).
  - Charge never goes past the cost. Once full, nothing adds more.
  - Passive: 5 per second (tf_ultimate_charge_per_second), but only while alive
    and only once the round is running and setup is over (doors open). Nothing
    during pre-round, setup or waiting for players.
  - Damage: 1 per point of health actually removed from enemy players and enemy
    buildings (tf_ultimate_charge_per_damage). Overkill doesn't count. The part
    of a hit that only removes overheal earns half
    (tf_ultimate_overheal_damage_scale 0.5). For example, 50 damage to a target
    20 HP above max earns 20 x 0.5 + 30 = 40.
  - Healing: 1 per point healed (tf_ultimate_charge_per_heal).
  - No charge from damaging yourself or teammates, or while the ultimate is
    active. Damage from an ultimate never counts: anything done while it's
    active, plus damage from entities an ultimate creates (projectiles, areas),
    which register with Ultimate_MarkEntity().
  - Use: +attack5 (default Q). With a duration, the charge drains evenly over
    it, and the ultimate ends when it's empty. Instant ultimates are spent at once.
  - Kept through death and respawn. Reset at every round start and when changing
    class. Dying while it's active ends it, and the charge is lost.
  - Self-healing: deferred, to be decided per hero and per ability. For now, any
    healing TF2 reports counts.

Where things live
-----------------
  src/game/shared/tf/tf_ultimate.cpp/.h  (new)
      All the rules above. The server owns the charge, and the owning player
      sees it over the network. Per-hero effect hooks are dispatched by class:
      Veteran_OnUltimateStart / Veteran_OnUltimateEnd (empty until the
      Veteran's ultimate effect is built). Also a round-start listener
      (teamplay_round_start) and the cheat command tf_ultimate_charge_set.
  Hooks in Valve's code, each marked // OWTF2:
      tf_classdata.h/.cpp      parse ultimate_cost / ultimate_duration
      tf_player_shared.h/.cpp  networked m_flUltimateCharge (points) and
                               m_bUltimateActive (they replace the earlier
                               Veteran-only 0-100 value); Ultimate_Think every
                               tick from ConditionGameRulesThink (it runs for
                               dead players too); Ultimate_PostFrame from
                               ItemPostFrame for the +attack5 key.
      tf_player.cpp            damage listener in OnTakeDamage_Alive. It uses
                               health before and after the hit, so overkill and
                               overheal are measured exactly.
      tf_obj.cpp               damage listener for buildings, where TF2
                               already counts real (non-overkill) damage.
      tf_gamestats.cpp         healing listener in Event_PlayerHealedOther.
                               Every healing source in TF2 reports there.
      in_buttons.h, in_main.cpp  IN_ATTACK5 (bit 27) and +attack5 / -attack5.
  HUD: the meter is now generic. CHudUltimateMeter (client/tf/tf_hud_ultimate.cpp,
      resource/ui/HudUltimate.res; renamed from the Veteran-only version) shows
      for any class with an ultimate and reads charge / cost. It pulses like
      Ubercharge when full and while the ultimate is active. It moved up to sit
      above TF2's objective HUD: the payload cart track covered it at the very
      bottom.
  Keys: Options > Keyboard lists +attack5 ("Ultimate ability", and "Veteran:
      Ultimate"). Q now defaults to +attack5 in kb_def.lst, config_default.cfg
      and the local config.cfg. It used to be lastinv (quick-switch).

How it was tested (VScript test on pl_badwater with a BLU bot, then removed)
------------------------------------------------------------------------------
  - Passive: 0 during pre-round and setup; +20.0 in the first 4 s after the
    doors opened.
  - Damage, each measured within one tick: full health 50 -> +50; all
    overheal -> +25; 20 overheal of 50 -> +40; self 20 -> +0; 100 on a 30 HP
    target -> +30.
  - Cap: passive filled to exactly 2310 and stopped. Damage when full -> +0.
  - Use: about 2125 half a second after Q, 1155 at 3 s, ended at 6 s. Damage
    while active -> +0.
  - Death: 1002.5 before death, while dead and after respawn. Dying while
    active -> inactive, 0.
  - Class change -> 0. Round restart -> 0.
  - HUD: 65% and 100% shown above the payload track.
  Not tested in game: healing (the Veteran can't heal anything yet), damage to
  buildings, and marked ultimate entities.

HUD position update: at the user's request, the ultimate meter now sits exactly
where the Medic's Ubercharge meter is (HudMedicCharge in TF2's hudlayout.res:
x r138, y r69; minmode r100 / r34), set in HudUltimate.res. Before this it was at
bottom centre above the objective HUD.

Ammo counter: the ultimate meter now takes the ammo counter's corner, so while
the meter is showing, the ammo counter (CTFHudWeaponAmmo, tf_hud_ammostatus.cpp/.h)
moves up to sit right on top of it. It reads the meter's real position, so it
also follows minimal HUD. It remembers the position hudlayout.res gave it and
goes back there when the meter is hidden: other classes, or a dead Veteran.
Checked in game: Veteran at 51% charge (ammo directly above the meter), then
Sniper (ammo in its normal corner).


=================================================
Helix rockets (rifle alt-fire)
=================================================

What it does
------------
Right mouse (+attack2, TF2's default MOUSE2 binding) fires one helix rocket, then
starts a 6 s cooldown (tf_veteran_helix_cooldown). Pressing during the cooldown
does nothing. The cooldown is reset on every spawn.

Placeholder: copy of the sentry rocket
--------------------------------------
tf_projectile_helix_rocket (CTFProjectile_HelixRocket, shared file
tf_projectile_helix_rocket.cpp/.h, server and client halves) is built like
CTFProjectile_SentryRocket:
  - model models/buildables/sentry3_rockets.mdl, zero-size hull (CTFProjectile_SentryRocket::Spawn)
  - speed 1100, blast radius 146, knockback: all from CTFBaseRocket, which the
    sentry rocket uses unchanged
  - damage 100 (tf_veteran_helix_damage, the sentry's value), never crits
  - normal rocket trail. The sentry rocket's client class looks like it turns
    trails off (CreateRocketTrails), but that function overrides nothing, so
    sentry rockets have the normal trail too.

Aiming: like the Rocket Launcher
--------------------------------
CTFWeaponBaseGun::FireRocket spawns the rocket at an offset from the eyes (23.5
forward, 12 right, -3 up; up 8 when crouched). CTFWeaponBase::GetProjectileFireSetup
then traces from the eyes along the crosshair, up to 2000 units, and points the
rocket from its spawn point at what the trace hit (or at the 2000-unit point).
That's the small, distance-dependent aim correction: close targets need a bigger
angle, far ones almost none. The helix calls the same function with the same
offset. The in-game test measured the rocket's flight direction against the
crosshair point: 0.00 degrees off.

HUD: like the Jarate/Mad Milk meter
------------------------------------
tf_hud_itemeffectmeter.cpp now registers the Veteran's rifle with the same
generic weapon meter the Jarate uses (CHudItemEffectMeter_Weapon, beeps on).
The rifle reports cooldown progress (GetEffectBarProgress / GetProgress) and the
label "#OWTF2_HelixRockets" ("HELIX"). The meter plays TF2's recharge sound when
it refills. The cooldown is the rifle's own networked, predicted timer
(m_flHelixReadyTime), not the Jarate's ammo-based recharge, which modern TF2
drives through item-schema charge-meter attributes.

Other changes: Options > Keyboard lists "+attack2" as "Veteran: Helix Rockets" in
the class-specific keys. New source files are in client_tf.vpc and server_tf.vpc.

Tested in game (pl_badwater, BLU puppet bot, VScript test, removed afterwards)
------------------------------------------------------------------------------
  - Rocket: tf_projectile_helix_rocket, sentry model, speed 1100, owner the
    Veteran, aimed exactly at the crosshair point.
  - Second press during the cooldown: nothing fired. Ready again after 6 s
    (fired again) and after respawn.
  - Hit: 175 -> 27 at 87 units (148 damage: base 100 plus TF2's close-range
    bonus, see Known issues).
  - HUD: the HELIX meter appears and refills.

Known issues (kept for later; functionality first)
----------------------------------------------------
  - The HELIX meter (TF2's item effect meter position, r162/r52) is drawn over
    the left edge of the ultimate meter (Medic meter position).
  - Damage uses TF2's normal distance modifier (+-50% around 512 units from the
    shooter): about 150 point-blank, about 50 far away. The Rocket Launcher gets
    half the close-range bonus; sentry rockets measure from the Engineer. To be
    decided, or switched off by removing DMG_USEDISTANCEMOD for this projectile.
  - The rockets hurt and push the Veteran like soldier rockets (the point-blank
    test shot took him from 125 to 118).
  - Placeholder launch sound (Building_Sentrygun.FireRocket) and third-person
    gesture (the primary attack's).
